# Coding Convention

Ці правила застосовуються до коду PageTracker: Node.js, JavaScript, React,
PostgreSQL, HTML і CSS. Основою для JavaScript є широко визнаний
[Google JavaScript Style Guide](https://google.github.io/styleguide/jsguide.html);
нижче наведено узгоджені з поточним стеком і структурою проєкту уточнення.

## JavaScript

- Використовуйте CommonJS (`require` та `module.exports`) і вказуйте `.js` у
  відносних шляхах імпорту. Не додавайте синтаксис чи залежності, що потребують
  збирача або транспілятора, без окремої зміни технологічного стеку.
- Для відступів використовуйте два пробіли, не табуляцію. Завершуйте інструкції
  крапкою з комою, використовуйте одинарні лапки для рядків і ставте кінцеву
  кому в багаторядкових літералах та списках аргументів.
- Використовуйте `const` за замовчуванням і `let`, лише якщо значення
  переприсвоюється. Для незмінних конфігураційних значень використовуйте
  `UPPER_SNAKE_CASE`.
- Використовуйте `camelCase` для змінних і функцій, `PascalCase` для класів і
  React-компонентів. Назви модулів без компонентів — у `kebab-case.js`;
  файли React-компонентів — у `PascalCase.js`.
- Вмикайте `'use strict';` на початку модулів. Надавайте перевагу невеликим
  функціям з однією відповідальністю та явним поверненням помилок замість
  приховування збоїв.
- Для асинхронного коду використовуйте `async`/`await`. Обробляйте помилки на
  межі, де можна надати контекст або коректно завершити операцію; не
  використовуйте порожні `catch` чи значення-запасні варіанти, що маскують
  помилку.

## React та браузерний інтерфейс

- Компоненти оформлюйте як функції з `PascalCase`-назвами; передавайте дані й
  обробники через props.
- Проєкт наразі не має JSX-трансформації, тому створюйте елементи через
  `React.createElement`. Не додавайте JSX, доки не буде узгоджено та налаштовано
  відповідну збірку.
- Використовуйте семантичні HTML-елементи, пов’язуйте підписи з полями форм і
  підтримуйте доступні назви елементів керування.

## API та PostgreSQL

- Дотримуйтеся наявного поділу на `api`, `application`, `infrastructure`,
  `security`, `time`, `observability` та `ui`; розміщуйте нову логіку в
  компоненті відповідної відповідальності.
- У JavaScript використовуйте `camelCase`; у SQL — `snake_case` для таблиць і
  колонок. SQL-ключові слова пишіть великими літерами.
- Передавайте значення запитів PostgreSQL параметрами (`$1`, `$2`, …), а не
  вставляйте їх у SQL-рядок.
- Перевіряйте форму та типи даних на межі API, а помилки повертайте у
  встановленому API-форматі. Зберігайте наявні контракти та ізоляцію даних
  користувачів.

## CSS

- Використовуйте два пробіли для відступів, `kebab-case` для класів і
  користувацьких CSS-властивостей.
- Групуйте правила за компонентом або сторінкою. Спільні кольори та інші
  повторно вживані значення оформлюйте CSS custom properties у `:root`.

## Тести та перевірка

- Пишіть тести на вбудованих `node:test` і `node:assert/strict`. Називайте
  файли `test-NN-topic.test.js` відповідно до наявних тестів.
- Ізолюйте тести від спільного стану. Інтеграційні тести PostgreSQL запускайте
  лише з `TEST_DATABASE_URL`, що вказує на окрему тестову базу.
- Перед передаванням змін запускайте `npm test` та `npm run lint`. ESLint
  перевіряє JavaScript у `src`, `tests` і `public` на основі рекомендованих
  правил ESLint та домовленостей цього документа.
- Зміни форматування через `npm run lint -- --fix` застосовуйте лише після
  перевірки diff; автофікси мають залишатися суто косметичними.
