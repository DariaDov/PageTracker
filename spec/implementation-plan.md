## Функціональне покриття REST API

REST API є серверним контрактом для клієнта PageTracker. Воно надає операції для всіх функцій облікових записів, книг, записів читання та статистики з SRS. Уточнення API, що не були визначені в SRS, погоджені як адендум під час API-GATE 2026-10-30; див. [api-contract-addendum.md](./api-contract-addendum.md). Нижче визначені URI, методи, параметри, тіла запитів, форми відповідей та HTTP-коди для кожної операції.

### Основні ресурси предметної області

| Ресурс | Призначення та зв’язки | Дані й правила SRS |
| --- | --- | --- |
| Користувач (`User`) | Власник бібліотеки та всіх пов’язаних даних. Один користувач має багато книг. | Ідентифікується обліковими даними; дані користувачів ізольовані. Пароль не зберігається відкрито. |
| Книга (`Book`) | Належить одному користувачеві; має нуль або більше записів читання. | Назва, автор, загальна кількість сторінок, статус і необов’язковий рейтинг. Статус і рейтинг обмежені правилами SRS. |
| Запис читання (`ReadingRecord`) | Належить одній книзі; фіксує послідовно прочитаний діапазон сторінок за автоматично визначену дату. | Початкова й кінцева сторінки та дата. Діапазони мають відповідати межам, неперетину й безперервності читання з SRS. |
| Статистика (`Statistics`) | Похідне подання записів читання користувача за календарний період; не є окремо створюваною чи редагованою сутністю. | Сума прочитаних сторінок, кількість днів періоду, що настали, та округлене середнє відповідно до SRS. |

Бібліотека — це колекція книг конкретного користувача, а не окрема сутність предметної області. Сесія й операції автентифікації потрібні API для керування доступом, але є службовими ресурсами, а не основними бізнес-сутностями. Позитивні й негативні сценарії API та їх зв’язки з REQ-ID наведені в [api-scenarios.md](./api-scenarios.md). Інструкції запуску mock-сервера й вибору прикладів помилок — у [mock-api.md](./mock-api.md).

### Схеми даних основних ресурсів

Схеми нижче використовують JSON Schema Draft 2020-12 і описують об’єкт ресурсу всередині оболонки `data` успішної відповіді (або елемент масиву `data` для колекцій). `additionalProperties: false` забороняє невизначені поля. Вхідні схеми наведені окремо від ресурсів, щоб клієнт не міг надсилати серверні та обчислювані значення.

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$defs": {
    "Id": {
      "type": "string",
      "minLength": 1
    },
    "User": {
      "type": "object",
      "additionalProperties": false,
      "required": ["id", "email"],
      "properties": {
        "id": { "$ref": "#/$defs/Id" },
        "email": {
          "type": "string",
          "minLength": 1,
          "pattern": "\\S"
        }
      }
    },
    "Book": {
      "type": "object",
      "additionalProperties": false,
      "required": ["id", "title", "author", "totalPages", "status", "rating"],
      "allOf": [
        {
          "if": {
            "properties": {
              "status": { "const": "прочитано" }
            }
          },
          "then": {},
          "else": {
            "properties": {
              "rating": { "type": "null" }
            }
          }
        }
      ],
      "properties": {
        "id": { "$ref": "#/$defs/Id" },
        "title": {
          "type": "string",
          "minLength": 1,
          "pattern": "\\S"
        },
        "author": {
          "type": "string",
          "minLength": 1,
          "pattern": "\\S"
        },
        "totalPages": {
          "type": "integer",
          "minimum": 1
        },
        "status": {
          "type": "string",
          "enum": ["розпочати", "читається", "прочитано"]
        },
        "rating": {
          "oneOf": [
            { "type": "integer", "minimum": 1, "maximum": 5 },
            { "type": "null" }
          ]
        }
      }
    },
    "ReadingRecord": {
      "type": "object",
      "additionalProperties": false,
      "required": ["id", "bookId", "startPage", "endPage", "pagesRead", "date"],
      "properties": {
        "id": { "$ref": "#/$defs/Id" },
        "bookId": { "$ref": "#/$defs/Id" },
        "startPage": { "type": "integer", "minimum": 1 },
        "endPage": { "type": "integer", "minimum": 1 },
        "pagesRead": { "type": "integer", "minimum": 1 },
        "date": { "type": "string", "format": "date" }
      }
    },
    "Statistics": {
      "type": "object",
      "additionalProperties": false,
      "required": [
        "period",
        "daysCounted",
        "pagesReadTotal",
        "hasData",
        "averagePagesPerDay"
      ],
      "properties": {
        "period": {
          "type": "object",
          "additionalProperties": false,
          "required": ["type", "startDate", "endDate"],
          "properties": {
            "type": {
              "type": "string",
              "enum": ["week", "month", "year"]
            },
            "startDate": { "type": "string", "format": "date" },
            "endDate": { "type": "string", "format": "date" }
          }
        },
        "daysCounted": { "type": "integer", "minimum": 1 },
        "pagesReadTotal": { "type": "integer", "minimum": 0 },
        "hasData": { "type": "boolean" },
        "averagePagesPerDay": {
          "oneOf": [
            { "type": "integer", "minimum": 0 },
            { "type": "null" }
          ]
        },
        "message": { "type": "string" }
      },
      "allOf": [
        {
          "if": {
            "properties": {
              "hasData": { "const": true }
            }
          },
          "then": {
            "properties": {
              "averagePagesPerDay": { "type": "integer", "minimum": 0 }
            },
            "not": { "required": ["message"] }
          },
          "else": {
            "properties": {
              "averagePagesPerDay": { "type": "null" },
              "message": {
                "const": "Щоб побачити статистику, додайте новий запис"
              }
            },
            "required": ["message"]
          }
        }
      ]
    },
    "Credentials": {
      "type": "object",
      "additionalProperties": false,
      "required": ["email", "password"],
      "properties": {
        "email": {
          "type": "string",
          "minLength": 1,
          "pattern": "\\S"
        },
        "password": {
          "type": "string",
          "minLength": 1,
          "pattern": "\\S"
        }
      }
    },
    "BookCreate": {
      "type": "object",
      "additionalProperties": false,
      "required": ["title", "author", "totalPages"],
      "properties": {
        "title": { "type": "string", "minLength": 1, "pattern": "\\S" },

      "type": "object",
      "additionalProperties": false,
      "minProperties": 1,

        "endPage": { "type": "integer", "minimum": 1 }
      }
    },
    "ReadingRecordPatch": {
      "type": "object",
      "additionalProperties": false,
      "minProperties": 1,
      "properties": {
        "startPage": { "type": "integer", "minimum": 1 },

}
```

`User` є лише безпечною публічною проєкцією облікового запису: пароль не входить ні до схеми ресурсу, ні до відповіді API; `Credentials` використовується лише для реєстрації/входу. Для пошти SRS не встановлює перевірку формату, тому схема не використовує формат `email`; вона відхиляє лише порожнє або пробільне значення. Унікальність пошти порівнюється з урахуванням регістру. `Book.userId` не передається: власника визначає сервер із сесії. `status` і `rating` у `Book` — серверні/контрольовані значення; рейтинг може мати значення 1–5 лише для `прочитано`, інакше він `null`. `BookCreate` їх не приймає, а `BookPatch` дозволяє змінити лише рейтинг у межах SRS. `ReadingRecord.date` і `pagesRead` є обчислюваними сервером значеннями; діапазони сторінок додатково перевіряються щодо загальної кількості, `endPage >= startPage`, перетинів, безперервності й статусу книги; `pagesRead = endPage - startPage + 1`. У `Statistics` поле `message` присутнє лише коли `hasData` дорівнює `false`; тоді `averagePagesPerDay` дорівнює `null`, інакше воно містить округлене середнє, де 0,5 округлюється вгору.

Межі періоду обчислюються в `Europe/Kyiv`; відповідь містить середнє та кількість днів у знаменнику або стан «немає даних». | REQ-F-001, REQ-F-015…018, REQ-F-038…040; REQ-I-005; REQ-NF-002 |

`{bookId}` і `{recordId}` — ідентифікатори ресурсів у шляху. URI не містять ідентифікатора власника: сервер визначає його з поточної сесії та перевіряє належність ресурсу користувачу. Окремі URI для списків книг і записів представляють колекції; URI з ідентифікатором — окремий ресурс. Перелік включає лише операції, необхідні для вимог SRS; створення користувацької сесії чи редагування облікового запису поза реєстрацією не передбачено.

### Загальні правила контракту

- Тіла запитів і успішних відповідей використовують `application/json; charset=utf-8`. Успішна відповідь із тілом має оболонку `{"data": ...}`. Будь-яка помилка повертає єдину модель Problem Details з `Content-Type: application/problem+json`; `204 No Content` не має тіла.
- Ідентифікатори (`id`, `bookId`, `recordId`) — рядки. Дати — календарні рядки `YYYY-MM-DD` у `Europe/Kyiv`. `status` книги має одне зі значень `розпочати`, `читається`, `прочитано`; рейтинг — ціле число 1–5 або `null`.
- Усі `/api/books`, `/api/reading-records` і `/api/statistics` операції потребують активної автентифікованої сесії; запит передає її cookie `pt_session` (непрозоре значення; `HttpOnly; Secure; SameSite=Lax; Path=/api`). Успішний вхід встановлює cookie через `Set-Cookie`, вихід завершує сесію та очищує cookie. Cookie не повертається в JSON і має залишатися чинним до явного виходу; сервер не завершує сесію автоматично (REQ-NF-005).
- Успішні коди: `200 OK` — читання або оновлення; `201 Created` — створення; `204 No Content` — успішне видалення чи вихід.
- Спільні HTTP-статуси помилок: `400 Bad Request` — некоректний синтаксис або параметр запиту; `401 Unauthorized` — немає активної сесії або неправильні облікові дані; `404 Not Found` — ресурсу немає або він не належить поточному користувачу; `409 Conflict` — конфлікт стану/унікальності; `422 Unprocessable Content` — синтаксично коректний запит з неприпустимими значеннями; `500 Internal Server Error` — технічна помилка без часткового збереження. Символічні коди, форма та правила повідомлень наведені в єдиній моделі помилки нижче.

### Єдина модель помилки API

Кожна помилка, включно з помилками автентифікації та технічними помилками, повертається як один об’єкт Problem Details. HTTP-статус у полі `status` завжди дорівнює фактичному статусу відповіді. `type` є стабільним URI-ідентифікатором типу помилки; `code` — стабільним машинним кодом для клієнтської логіки; `title` — коротким заголовком типу помилки; `detail` — безпечним повідомленням для користувача; `instance` — шляхом запиту, що спричинив помилку. `errors` — необов’язковий список помилок окремих полів, де `pointer` є JSON Pointer до поля запиту. Жодне поле не містить stack trace, SQL, внутрішніх повідомлень чи секретів.

```json
{
  "type": "urn:pagetracker:problem:VALIDATION_ERROR",
  "title": "Некоректні дані",
  "status": 422,
  "code": "VALIDATION_ERROR",
  "detail": "заповніть дані",
  "instance": "/api/books",
  "errors": [
    {
      "pointer": "#/title",
      "code": "REQUIRED",
      "message": "заповніть дані"
    }
  ]
}
```

Схема Problem Details (JSON Schema Draft 2020-12):

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "additionalProperties": false,
  "required": ["type", "title", "status", "code", "detail", "instance"],
  "properties": {
    "type": { "type": "string", "format": "uri" },
    "title": { "type": "string", "minLength": 1 },
    "status": {
      "type": "integer",
      "enum": [400, 401, 404, 409, 422, 500]
    },
    "code": {
      "type": "string",
      "enum": [
        "INVALID_JSON",
        "INVALID_PARAMETER",
        "AUTH_REQUIRED",
        "INVALID_CREDENTIALS",
        "EMAIL_ALREADY_EXISTS",
        "NOT_FOUND",
        "STATE_CONFLICT",
        "VALIDATION_ERROR",
        "INTERNAL_ERROR"
      ]
    },
    "detail": { "type": "string", "minLength": 1 },
    "instance": { "type": "string", "minLength": 1 },
    "errors": {
      "type": "array",
      "items": {
        "type": "object",
        "additionalProperties": false,
        "required": ["pointer", "code", "message"],
        "properties": {
          "pointer": { "type": "string" },
          "code": { "type": "string", "minLength": 1 },
          "message": { "type": "string", "minLength": 1 }
        }
      }
    }
  }
}
```

| HTTP-статус | `code` | Використання |
| --- | --- | --- |
| `400` | `INVALID_JSON` | Тіло запиту не є коректним JSON. |
| `400` | `INVALID_PARAMETER` | Некоректний query/path-параметр або невідоме поле запиту. |
| `401` | `AUTH_REQUIRED` | Для захищеної операції немає чинної сесії. |
| `401` | `INVALID_CREDENTIALS` | Неправильна пошта або пароль під час входу. |
| `404` | `NOT_FOUND` | Ресурс не знайдений або не належить поточному користувачу; ці випадки не розрізняються у відповіді. |
| `409` | `EMAIL_ALREADY_EXISTS` | Реєстрація з уже зайнятою поштою. |
| `409` | `STATE_CONFLICT` | Операція несумісна з поточним станом ресурсу: рейтинг не завершеної книги, зміна кількості сторінок після записів, заборонена зміна/видалення запису або конфлікт діапазонів. |
| `422` | `VALIDATION_ERROR` | Коректний за синтаксисом запит порушує обмеження полів чи бізнес-правила; за можливості додається `errors`. |
| `500` | `INTERNAL_ERROR` | Непередбачена технічна помилка. `detail` завжди має бути «Помилка»; внутрішні подробиці не повертаються, зміни не зберігаються частково. |

`EMAIL_ALREADY_EXISTS` і `INVALID_CREDENTIALS` мають однаковий користувацький `detail`: «Неправильні дані» (REQ-F-030); клієнт не показує користувачу сирий `code`. Для інших помилок `detail` або `errors[].message` містять відповідний текст SRS: «заповніть дані», «Ці сторінки вже прочитані», «Кінцева сторінка, менша за початкову», «Будь ласка, змініть сторінку», «Відсутні сторінки», «Видалення заборонене». Відсутня книга/запис або чужий ресурс однаково дають `404 NOT_FOUND`. Технічна помилка статистики використовує ту саму модель з `500 INTERNAL_ERROR` і `detail: "Помилка"` (REQ-F-040).

Усі операції використовують наведену вище єдину модель помилки та реєстр `code` ↔ HTTP-статус; відповідь помилки не має окремої обгортки `error` і не змінює поля для різних ресурсів.

Усі операції з приватними даними мають застосовувати однакові правила SRS: користувач бачить і змінює лише власні дані; сервер сам встановлює дату запису й обчислює статус книги; створення, редагування та видалення зберігають цілісність прогресу й одразу відображаються у статистиці. Невалідна операція не змінює дані частково. Пагінація бібліотеки повертає по 16 книг; список записів не має пагінації. Реєстрація та вхід дотримуються правил пошти й пароля SRS, а зайнята пошта та неправильні дані входу мають однаковий результат «Неправильні дані».

API підтримує наскрізні вимоги щодо HTTPS, захищеного зберігання паролів, збереженості між сесіями, атомарності та місткості (REQ-NF-003…007). За 10 активних користувачів операції входу, відкриття бібліотеки, створення запису та отримання статистики мають вкладатися у 2 секунди (REQ-NF-002). Автоматизовані тести API входять до TEST/VER відповідних функціональних етапів і повної регресії (REQ-NF-008, REQ-NF-009).

Вимоги `REQ-I-*` про сторінки, навігацію, українські написи, форми, діалоги підтвердження та переходи після дії залишаються вимогами браузерного клієнта, а не REST API. API повертає результат операції та розрізнювані причини відмови, щоб клієнт міг відтворити повідомлення й поведінку, визначені SRS; зайнята пошта та неправильні дані входу не розрізняються. Цей розділ не додає окремих функцій поза SRS.

## Критичний шлях і дозволений паралелізм

```text
SPEC-01 → ADD-01 → GATE-00 → FEAT-01 → VER-01 → VAL-01 → GATE-01
GATE-(n-1) → TEST-n; TEST-n + VER-(n-1) + VAL-(n-1) → GATE-n
GATE-n → FEAT-n → VER-n → VAL-n, для n = 2…11
VER-11 + VAL-11 → GATE-12 → TEST-12 → VER-12 → VAL-12 → DOC-01 → GATE-13
```

### Визначений критичний шлях

За поточними залежностями критичним є послідовний ланцюг етапів:

```text
P0 Узгодження → GATE-00 → P1 Каркас → GATE-01
→ P2 Реєстрація/доступ → GATE-03 → P3 Бібліотека → GATE-05
→ P4 Деталі та записи → GATE-08 → P5 Керування даними
→ P6 Статистика → GATE-12 → P7 Фінальна перевірка → GATE-13
```

У термінах тікетів критичними є всі `FEAT-01…FEAT-11`, їхні `VER-01…VER-11`, людські `VAL-01…VAL-12`, усі рішення `GATE-00…GATE-13`, а також `TEST-12`, `VER-12` і `DOC-01`. Затримка будь-якого з них не має планового резерву та безпосередньо зміщує завершення проєкту.

| Набір задач | Чому впливає на строк | Умова контролю |
| --- | --- | --- |
| SPEC-01, ADD-01, GATE-00 | Без них неможливо почати каркас. | GATE-00 прийнято людиною. |
| FEAT-01, VER-01, VAL-01, GATE-01 | Єдина передумова переходу до функціональних робіт. | Каркас верифікований і валідований. |
| FEAT-02…FEAT-11, VER-02…VER-11, VAL-02…VAL-11, GATE-02…GATE-11 | Кожен наступний функціональний Feature заблокований результатом попереднього етапу й рішенням людини. | На кожному переході є докази Verification і людське рішення. |
| GATE-12, TEST-12, VER-12, VAL-12, DOC-01, GATE-13 | Це єдиний шлях до інтеграції або релізу. | Повна регресія успішна, документація оновлена, GATE-13 відкрито людиною. |

`TEST-02…TEST-11` є **умовно критичними**: їх можна готувати паралельно з поточним `FEAT`, але відповідний тест має бути завершений у початково непрохідному стані до рішення `GATE-n`. Якщо тест не готовий у цей момент, він стає прямим блокером і входить до критичного шляху. За відсутності паралельного виконавця ці тести слід вважати критичними відразу.

Точне правило переходу для кожного функціонального номера `n = 2…11`:

```text
попередній Gate дозволив підготовку TEST-n
TEST-n (спершу не проходить) + VER-(n-1) + VAL-(n-1)
  → людське рішення GATE-n
  → FEAT-n → VER-n → людська VAL-n
```

`TEST-(n+1)` можна готувати після відкриття `GATE-n`, паралельно з `FEAT-n`, але `FEAT-(n+1)` залишається заблокованим до закриття `VER-n`, людської `VAL-n` і людського `GATE-(n+1)`. Це скорочує активний строк без порушення TDD або делегування контрольних рішень агенту.

| Перехід | Обов’язкові передумови | Хто приймає рішення |
| --- | --- | --- |
| Початок FEAT-01 | SPEC-01 і ADD-01 завершено; GATE-00 відкрито. | Людина |

| Початок фінальної перевірки | VER-11 і VAL-11 завершено; GATE-12 відкрито. | Людина |

## Вимоги посиленого контролю

До цієї групи належать вимоги, відмова яких може спричинити витік даних, незворотну втрату або спотворення даних користувача, недостовірний результат статистики чи неможливість безпечно продовжити роботу. Це не нові функції: нижче визначено лише додатковий контроль уже наявних REQ-ID.

## Ризики для строку

- Найбільший функціональний ризик зосереджений у етапах 5–6: правила безперервності, незворотний статус `прочитано` і заборона видалення з розривом. Їхні BDD-сценарії мають бути реалізовані в TEST-08 і TEST-09 до коду.
- Етап 8 може збільшити строк, якщо фактичні вимірювання не вкладаються у REQ-NF-002 або REQ-NF-007; це повертає роботу до відповідного `Feature`, після чого потрібні повторні `Verification`, `Validation` і Gate.
- Очікування людського рішення не маскується оцінкою: без закритого `VAL` та відкритого `GATE` наступний `Feature` не стартує.
