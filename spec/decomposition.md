# Первинна декомпозиція SRS PageTracker

**Джерело:** `spec/specification.md`, версія 1.0.
**Принцип:** базові пункти посилаються на вимоги SRS; зміни поза його межами вимагають окремого схваленого адендуму, який є нормативним джерелом додаткових `REQ-*`. Пункти з `REQ-*` є одиницями планування; технічні кроки не додають користувацької функціональності. Порядок — рекомендований, з урахуванням залежностей.

## Правила виконання для всіх робіт

- Для функціональних вимог спочатку додається автоматизований тест, який відтворює критерій прийняття або BDD-сценарій, і лише потім реалізація (`REQ-NF-008`).
- Перед інтеграцією повний набір таких тестів має проходити (`REQ-NF-009`).
- Інтерфейс і повідомлення виконуються українською, у браузері (`REQ-I-001`, `REQ-I-002`), а дані зберігаються між оновленням сторінки та новим входом (`REQ-NF-004`).
- Роботи не охоплюють можливості, прямо виключені з v1 у розділах 1 і 7 SRS.

## Ролі та межі делегування

| Тип тікета | Основний виконавець | Участь агента | Рішення людини |
| --- | --- | --- | --- |
| Specification | Людина | Може структурувати наданий текст, знайти суперечності й підготувати пропозиції; не змінює зміст або пріоритет вимоги самостійно. | Затверджує SRS, межі v1 та зміни вимог. |
| Addendum | Спільно | Готує декомпозицію, простежуваність, залежності й чернетки уточнень на основі SRS. | Підтверджує кожне уточнення, що змінює зміст, обсяг або трактування SRS. |
| Test | Переважно агент | Створює й запускає автоматизовані тести за ID вимог; фіксує початковий стан тесту, що не проходить. | Вирішує суперечності в критеріях прийняття та погоджує неоднозначні тестові трактування. |
| Feature | Переважно агент | Реалізує лише поведінку, покриту готовим `Test` і дозволену відповідним `Gate`; запускає локальні перевірки. | Погоджує будь-яке відхилення від затвердженого SRS або зміну обсягу. |
| Verification | Спільно | Запускає автоматизовані, регресійні, технічні та нефункціональні перевірки; надає відтворювані результати. | Аналізує ризики, які не можна обґрунтувати автоматично, та підтверджує достатність доказів. |
| Validation | Людина | Може підготувати демонстрацію, чекліст за REQ-ID і зібрати докази; не робить висновок про відповідність задуму. | Виключно людина підтверджує, що результат відповідає задуму, потребі та затвердженому SRS. |
| Documentation | Переважно агент | Оновлює матрицю простежуваності, технічну й користувацьку документацію за фактичними результатами. | Перевіряє та затверджує зміст, який описує домовленості, рішення або зовнішні зобов’язання. |
| Gate | Людина | Може лише показати стан залежностей, результати тестів і перелік ризиків. Не може відкрити, закрити або обійти Gate. | Виключно людина приймає рішення «дозволити» або «заборонити» перехід до наступного етапу. |

Агент не має права самостійно закривати `VAL-*` або `GATE-*`. Статус `VAL-*` встановлює людина після валідації задуму; стан `GATE-*` встановлює людина після перевірки залежностей, результатів `Verification` і відповідної `Validation`.

## Реєстр Feature-тікетів

`Feature` є єдиним типом у цьому реєстрі, який реалізує поведінку. Кожен `FEAT-01…FEAT-11` заблокований своїм `TEST`; отже реалізацію не можна починати, доки тест не створений. `GATE-00` відкриває початковий етап, а кожен наступний Gate закриває перевірений етап і відкриває підготовку наступного тесту. `FEAT-01` — лише технічний каркас, а не реалізація функціональної вимоги. ## Правило залежностей і блокування

```text
SPEC-01 → ADD-01 → GATE-00 → TEST-01 → FEAT-01 → VER-01 → VAL-01 → GATE-01
GATE-n → TEST-(n+1) (спочатку не проходить) → FEAT-(n+1) → VER-(n+1) → VAL-(n+1) → GATE-(n+1), n = 1…10
GATE-11 → TEST-12 → VER-12 → VAL-12 → GATE-12 → DOC-01 → GATE-13
ADD-02 → SPEC-ADDENDUM-GATE-02 → TEST-GATE-13 → TEST-13 (RED) → FEAT-12 → VER-13 → VAL-13 → GATE-14
```

Для `n = 1…11` `FEAT-n` блокує `TEST-n`. Закриття `TEST-n` означає, що тест уже додано й він відтворює вимогу, але до реалізації очікувано не проходить; це не замінює `VER-n` після реалізації. `GATE-n` не виконує тестів і не створює коду: його закривають після завершення відповідних TEST, FEAT, VER і VAL як рішення про перехід до наступного етапу.

## Межі готовності робіт

- **TEST-01—TEST-11:** для кожного згаданого `REQ-F-*` / `REQ-I-*` є тест, доданий до реалізації, що перевіряє точний результат або повідомлення SRS.
- **TEST-13:** покриває вимоги схваленого ADD-02 до FEAT-12; тести доводять межі періодів, збереження, ізоляцію, атомарність, помилки та оновлення прогресу.
- **VER-01, VER-03, TEST-12:** покривають ізоляцію, збереженість, безпеку зберігання пароля, атомарність і місткість відповідно до зазначених `REQ-NF-*`.
- **TEST-08, TEST-09, TEST-11:** окремо покривають чотири ключові сценарії SRS: завершення книги, пропуск сторінок, заборону видалення проміжного запису й відсутність статистики.
- **GATE-13:** може бути закритий лише після зафіксованого успішного регресійного прогону; функції поза SRS не додаються.

## Покриття ID

Усі вимоги базового SRS розподілено: `REQ-F-001…043`, `REQ-I-001…019` і `REQ-NF-001…009`. Додаткові вимоги `REQ-F-044/045`, `REQ-I-020` і `REQ-NF-010` належать схваленому ADD-02 та не змінюють SRS v1.0. Вимоги, що спільно формують один користувацький сценарій, залишені в одній роботі; їхні ID не замінені узагальненими назвами.
